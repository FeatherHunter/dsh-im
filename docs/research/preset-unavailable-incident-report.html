故障调查结论：飞书机器人高频报 PRESET_UNAVAILABLE

基线 main = upstream/main = 1fa86ed ｜ 运行树 private/custom ｜ 调查方式：4 路对抗审查 + Host 本体取证 ｜ 报告生成：HTML 单文件

一、场景复述（发生了什么）

人物与链路：用户“猎羽”在飞书私聊里与机器人“小孙”对话。“小孙”是 dsh-im 飞书桥接的一个 bot，背后连着一台 DeepSeek Harness（DSH）Host，当前绑定的 Harness 会话是 session-4ba8e999-9db7-4a74-b49b-c648ad2a439f（创建时 preset=ptc，人设是第一性原理健身教练）。

完整交互时间线（同一私聊，从上到下）：

#用户发的机器人回的session 日志
1hello❌ PRESET_UNAVAILABLE（MF-AC71ACB7）不在（创建即被拒，进不了会话）
2/presetlist跟随 Host 默认 ptc；目录 4 项全健康不在（命令不建会话，正常）
3/preset 1已设为 standard（注明：已有会话不变，需 /new）不在（命令不建会话，正常）
41✅ 增肌长文turn 4 ✅
51✅ 定量追问turn 5 ✅
6hello✅ 正常回答turn 6 ✅
7你是谁✅ 正常回答turn 7 ✅
8卡路里 help❌ 先“小孙 撤回了一条消息”，再 PRESET_UNAVAILABLE（MF-C3FF35A8）不在（本次新建被拒）；但该 session 的 turn 2 有另一次同文本的成功记录

三个反直觉、但全部属实的现场特征：① 存量已是合法的 standard、目录里也有 standard，还炸；② 同文本“卡路里 help”一成一败，与内容无关；③ “撤回”是机器人自己撤占位流式卡（失败清理），不是用户撤的。session 日志“缺消息”不是丢消息——命令消息、创建失败的消息本来就进不了任何会话。

二、原因分析

2.1 端到端因果链

  1. 该聊天是私聊，会话键只按发送人算（src/channels/feishu/message-utils.mjs:29-44，运行树与 main 一致），线程/引用不参与——全聊共享同一绑定。
  2. 有可用绑定时直接复用老会话（workspace-session.mjs:68-71）→ turn 4–7 全部成功，且继续跑在老 ptc 会话上（/preset 1 只影响未来新会话，文档与实现一致）。修正：复用不是“不碰 preset”——Host 在每次 prompt/resume 时会重验会话自带的 preset，这正是本案失败点（见下条）。日志实锤：session.prompt: resume failed … preset "code" not found (available: standard, ptc, minimal, cordis)。
  3. “卡路里 help”到达时复用了另一个 key 下的老绑定 session-df49901a…（同类还有 session-7db1fb21…），这两个会话创建于 code 时代；Host 在 resume 时重验其自带 preset → preset "code" not found。新建分支的盲透传（bot-workspace-store.mjs:1346-1352）在本案中不是触发点——触发点是死绑定的复用，而 /preset 只改未来新会话，救不了已绑定的死会话。
  4. Host 拒收。B 线在 DSH 本体包内钉死：校验分两阶段——composeAgent 只 resolve 判存在，agent 发布前 setup 才 mount 判可挂载并整体回滚；list 零缓存每次重读。所以“列表里有 standard、创建时拒 standard”结构性成立，Top1 是 mount 期审计失败（未激活行 / root realm 服务泄漏 / 文件不可读），另有 TOCTOU 目录竞争、大小写精确匹配、默认指针热重载等 9 项并列可能。
  5. 失败后占位流式卡被 recall（feishu-channel.mjs:267-271），再发出错误文本——“撤回 + 报错”是固定输出对，与截图完全吻合。
  6. 死绑定永远不清，下一条继续复用它继续失败（粘性循环）→ 一次卡住、条条卡住，这就是“3~4/5、每个普通消息都遇到”的数学原因。而 /preset 改的是另一个维度的配置，所以用户越改越困惑。

2.2 必须如实记录的两个分歧

① 线程换 key 不适用于本现场：C 线的 thread 分流只影响群聊话题；本现场是私聊，成功与失败是同一 key，差异只能来自绑定/会话丢失，而非 key 分叉。

② 斜杠 vs 连字符版本错位：dsh-im 分类器只认连字符 agent-preset-（message-failure.mjs:136）；checkout 内 Host 2.0.5 只发斜杠 agent-preset/*，且仓内无任何翻译层（harness-client 零命中）。斜杠码只会掉进 INTERNAL_UNKNOWN，变不出用户看到的 PRESET_UNAVAILABLE——故用户运行期的 Host 说的是连字符，存在版本错位。连带发现一个前向兼容 bug：Host 升级到斜杠码后，preset 拒绝会被误渲染成 INTERNAL_UNKNOWN。

2.3 根因排名

排名根因说明
1死绑定复用：老会话自带已下架的 code，Host 每次 resume 重验必拒（日志实锤）与 /preset=standard 无关，是两个维度的配置；/preset 救不了已绑定的死会话
2失败粘性放大建不出会话就不存映射，下条必重试 → 体感 100%
3报错脱敏不带被拒 ID只能看到反复炸，看不到炸的是哪个值
4复用掩盖真相老会话活着时一切正常，新建才爆，时好时坏

三、解决办法

已落地的代码修复（本次调查直接产出）

  1. 死绑定自愈（workspace-session.mjs）：复用绑定的 ask 若以 preset 不可用失败， retire 该绑定一次并用机器人当前 preset 建新会话重试；新建即失败或二次失败照常报错，绝不死循环。回归用例 test/workspace-session-heal.test.mjs（5 个）全过。
  2. 兼容 Host 新码（message-failure.mjs）：agent-preset/… 斜杠码同样归一 PRESET_UNAVAILABLE，并导出 isPresetUnavailableFailure 供自愈判定。
  3. 报错点名：失败对象携带 presetId（仅小写合法 ID，防泄漏），文案追加“出问题的 Preset：code”，尾部错误码/参考号格式不变，中英双语。
  4. 回归：message-failure 6/6、新自愈 5/5、飞书桥 149/149 通过；另有两个预先存在的环境失败（Windows 路径断言、symlink EPERM），干净树同现，与本次改动无关。

立即止血（用户可做，一条命令）

在出事的聊天里发 /new——丢掉 code 时代的死绑定，用当前 standard 建新会话，下一条消息即恢复。这就是之前 /preset 不起作用的原因：它只管未来新会话，管不了已绑定的死会话。
  1. 出事聊天发 /preset --default，再 /new，重发普通消息（绕开存量直连 Host 默认）。
  2. 重发一次 /presetlist 确认 standard 是否仍在目录（4 项是否齐）。
  3. 取 dsh web 日志里 MF-C3FF35A8 / MF-AC71ACB7 两行的原始 code/method/details（搜 failed [MF-…]），这是定案证据；同时确认 DSH Desktop 版本号。

代码修复（按顺序）

  1. 分类器兼容斜杠码（agent-preset/ → PRESET_UNAVAILABLE），否则下个 Host 版本全变 INTERNAL_UNKNOWN。
  2. 错误文案回显归一化后的 preset ID（自有数据，不泄密）。
  3. 新建连续失败熔断：提示切 --default，打破无限重试。
  4. main 落地大小写归一与 code→standard 迁移（参照 b73901a）。
  5. 补 G1/G2 用例：bridge preset 失败分支、坏文件 load 行为。

结论（已更新）：日志实锤根因为死绑定复用——code 时代的老会话在每次 resume 时被 Host 拒绝，与存量 standard 无关；“列表有、创建拒”的 mount 期/TOCTOU 机制仍是同类故障的结构性成因，已保留。同类死循环已由死绑定自愈修复覆盖；斜杠码兼容与报错点名已落地。Host 两阶段校验与 mount 审计细节见 B 线报告。
